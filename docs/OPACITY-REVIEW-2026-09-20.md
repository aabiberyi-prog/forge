# 全窗口透明度修复与验收

用户要求先提交上一轮截图编辑体验修复，再修复所有功能的透明度。上一轮 11 个文件已提交为 `dcd094ca0941737d25a3df4b3e159926d5870dd8`，推送到 `origin/repair/phase-6-accept`，远端提交号已回读核实。本文件记录其后的透明度修复，尚未提交。

## 范围与原因

按 9 类界面逐一检查：翻译、OCR、设置、更新、截图编辑、贴图历史、TODO/剪贴面板、贴图、截图框选。

- 原生后端虽向部分窗口发送 `window_opacity`，但只有翻译组件监听并使用透明度；设置页左右背景固定为 90%/100%，OCR 和贴图历史为 100%。现场把值改为 25% 后，翻译根背景变为 rgba(...,0.25)，其他窗口背景和 CSS 变量未变。
- 上一轮截图编辑器使用了固定深色背景，未接入全局透明度。这次把各背景区域接入同一变量，截图像素本身仍保持不透明。
- 翻译窗口收到透明度事件后再次写配置，形成重复写入路径。改为 App 统一读取配置事件，接收方只更新显示；原生更新发布现有的 `window_opacity_changed`，让窗口和滑块都同步。
- 贴图的图像虽然改变 opacity，但根容器还有 40% 黑底，造成“图像变淡、底层仍发黑”。黑底移到操作栏，图像区域下方保持透明。
- 正式配置的全局值为 1.0、面板值为 0.85。数值较高本就更不透明，是另一项影响观感的因素；中文现在明确称为“不透明度”，并说明 100% 为完全不透明，没有擅自改低用户的原值。

历史核对：`70868c46ee` 已将整个 HWND 的淡化改为 shell-only opacity。因此本轮保持原文/译文内容卡片不透明，控件和文字不使用父元素整体 opacity；修复的是背景设置的覆盖、同步和贴图自身的不透明度。

## 实现

1. `App.jsx` 为各窗口统一初始化并响应背景变量，关闭“透明效果”时背景恢复 100%，重新开启时恢复保存值。
2. 翻译、OCR、设置、更新、截图编辑、贴图历史的背景消费同一变量；设置页卡片也响应。移除翻译组件重复事件回写。
3. 设置和翻译两个滑块双向同步，拖动有预览，操作结束立即调用原生保存；总开关关闭时滑块禁用并有说明。
4. TODO 继续使用自己的面板设置和悬停增亮；贴图继续使用独立图像滑块及重置功能。全局背景不覆盖这两个独立值。
